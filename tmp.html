Zig is a systems-level programming language with modern features. It is designed to be simple, explicit and easy to maintain, and to give you full control over your computer. A security vulnerability is a way of using software, not intended by the developer, that compromises security, whether that's more access, data exposure or something else. Compilers transform code written in modern languages into assembly. They can produce that assembly in different ways depending on what the developer wants. For example, when debugging, the compiler can keep runtime safety checks and debug info and skip optimisation, so errors are caught and reported with a location when they happen. These safety checks and debug info slow the program down, so they may be turned off in time-critical applications. In Zig this choice is called the release mode, and there are four: Debug, ReleaseSafe, ReleaseFast and ReleaseSmall. When choosing how the compiler should compile their program, developers need to know the trade-offs between building it in ReleaseSafe and building it in ReleaseFast (if speed is what they want). What security vulnerabilities do they need to worry about when building in ReleaseFast compared to ReleaseSafe? Is the switch worth the extra speed? These are safety considerations everyone building a program in Zig has to decide on. The gap: developers are unsure exactly which vulnerabilities they are exposed to when building in different release modes, and what performance trade-offs the safety checks bring. Because Zig is new, I could not find any published work formally running and measuring the effects of release modes. Knowing the risks and costs of release modes could be the difference between a major security vulnerability and missing a stock exchange trade by a fraction of a millisecond. Having this knowledge helps developers make an informed decision about what is best for their software. And in the cases where producing code that runs as fast as possible is advantageous, knowing the security implications is important not only for the developer but also for everyone who uses the software. To gather this data, I propose running experiments in the different release modes on known vulnerable programs. I would measure speed, safety and executable size, not only by looking at each mode as a whole but also by looking at which specific techniques in each mode make the most difference to what developers want to achieve. This would then give a clear view of the trade-offs between safety, speed and size. These measurements would then feed into looking at real Zig code, to see whether people are using the release modes wrongly, with examples from real projects. From there, I want to see whether there is a benefit to having more control over the compiler. Zig already has @setRuntimeSafety, which turns runtime safety checks on or off for a scope, but I think this may be too broad. Instead, I would look at a custom profile that sits partly in the middle of the existing modes, rather than just Safe, Fast and Small: for example, a list of individual checks that the developer can turn on or off.
